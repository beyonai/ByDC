# 演示场景指南

> 本文件提供产品理念演示话术、FAQ 应答策略和演示时间分配方案。具体的演示步骤和命令请参考 SKILL.md。

## 一、产品理念演示

以下五个理念对应 README.md 五大核心能力。演示时建议按顺序进行，每个理念的演示都建立在前面演示的成果之上。

### 1.1 业务本体语义层

**README 原文**：通过业务对象 + 关系 + 规则构建公司级语义网络，解决数仓只汇总数据、AI 听不懂业务语义的问题；`col_id_002` 变成"客户编号"，大模型真正理解业务含义。

**演示方式**：

1. 先展示一个底层字段 ID，例如 `col_id_002`，询问用户"您猜这个字段代表什么？"。
2. 在系统中查询该术语的 name 映射：`col_id_002` → "客户编号"。
3. 解释：传统数仓中字段以编码形式存在（col_id_001、col_id_002），大模型无法理解其含义；本体语义层将这些编码映射为业务人员能理解的名称，形成公司级语义网络。
4. 再随意抽查几个术语映射，展示整个术语体系覆盖了 CRM 核心业务领域（如"签约金额""商机贡献度""所属行业"等）。
5. 总结：本体语义层就是"翻译官"，把机器语言翻译成业务语言，再反向把用户的自然语言翻译成机器可执行的查询。

**关键展示点**：col_id_002 → "客户编号" 的映射演示，术语体系覆盖度展示。

### 1.2 零 ETL 联邦查询

**README 原文**：通过数据虚拟化 + 跨源联邦计算，解决数据散在多个异构数据库、AI 无法跨源分析的问题；数据原地不动，无需搬运，实时跨源查询。

**演示方式**：

1. 先说明 CRM 数据（客户、商机、项目）存放在一个数据源，通讯录/组织架构数据存放在另一个数据源。
2. 执行一次跨源查询：例如查询"华北-金融组的销售黄药师负责哪些客户？"—这涉及组织表（组织架构数据源）→ 销售人员表 → 客户表（CRM 数据源）的跨源关联。
3. 展示查询结果，强调系统在背后自动完成了跨源路由、字段映射、计算联邦——用户完全无感。
4. 对比传统 ETL 方案：传统做法需要搭建数据管道、定时同步、处理增量变更；零 ETL 方案数据原位不动，实时直查。

**关键展示点**：跨数据源的联合查询 → 用户无感的跨源路由 → 与传统 ETL 的对比说明。

### 1.3 异构数据融合

**README 原文**：通过对非结构化文档进行结构化标签增强，建立文档与业务对象的双向关联，解决结构化查询与文档检索割裂、无法联合分析的问题。

**演示方式**：

1. 前提：前面已完成客户查询（结构化）和拜访记录创建（非结构化）。
2. 查询客户"广州国投中债资产管理有限公司"的完整信息——除结构化字段（客户编码、名称、行业、省份）外，系统同时关联出对应的拜访记录文档（如"拜访-广州国投中债-20260507"的纪要摘要）。
3. 解释融合的关键：客户表中的"客户编码"字段，与拜访记录中的"客户名称"通过本体语义层的映射建立关联——同一个业务实体在两个不同形态的数据源中被打通。
4. 反向演示：在拜访记录中查询"黄药师"的拜访历史，系统同时展示每条拜访记录对应的客户结构化信息（行业、省份等）。
5. 总结：结构化字段提供精确筛选和统计能力，非结构化文档提供细节和上下文——两者融合后，数据洞察更完整。

**关键展示点**：结构化字段 + 非结构化文档在同一结果中联合展示；双向关联（从客户查文档，从文档查客户）。

### 1.4 性能与准确率双保障

**README 原文**：通过自建 DSL 规则引擎，简单任务优先走规则路径保证响应速度，复杂任务自动降级到 text2SQL 兜底，解决大模型数据查询普遍慢且不稳定的问题。

**演示方式**：

1. 先执行一次简单查询：使用前面创建的"产品订单视图"，查询"各产品的订单总金额"。
2. 记录响应速度：视图查询一次返回，速度快（秒级）。
3. 对比说明传统方式：如果不用视图，需要先查产品表获取所有产品 → 按产品编码分别查订单表 → 手动汇总。多轮查询的网络往返和结果拼接会显著增加耗时。
4. 解释背后机制：简单查询被 DSL 规则引擎直接命中 → 生成优化执行计划 → 单次查询返回；复杂查询无法命中规则时，自动降级到 text2SQL 路径，由大模型生成 SQL 后执行，保证准确率。
5. 强调"双保障"的含义：规则路径保证速度，text2SQL 路径保证兜底——快的时候不牺牲准确，难的时候不牺牲可靠。

**关键展示点**：视图查询秒级返回 vs 传统多次 join 的效率对比；规则引擎 + text2SQL 双路径说明。

### 1.5 操作安全人工确认

**README 原文**：所有数据操作类 API 在执行前均弹出确认表单，由人工审核后方可执行，解决 AI 自动操作数据存在误操作风险的问题；查询自动执行，操作必须确认，边界清晰。

**演示方式**：

1. 在前面数据操作演示中，用户提交"客户录入"时，系统弹出确认表单——展示即将写入的完整数据（客户名称、编码、行业、省份等），等待用户确认。
2. 强调：在用户点击"确认"之前，数据不会真正写入数据库——这是一个安全护栏。
3. 说明查询与操作的边界：查询类操作（只读）自动执行，无需确认；数据操作类（增、删、改）必须经由人工确认后才执行——"查询自动，操作确认"。
4. 补充说明权限校验插件（建设中）：未来会在确认之前增加一层数据权限校验，用户只能看到和操作自己权限范围内的数据，进一步降低误操作和数据泄露风险。

**关键展示点**：录入前确认表单展示 → "查询自动，操作确认"的边界说明 → 权限校验插件的未来规划。

## 二、FAQ 演示策略

当用户在演示过程中提出以下常见概念类问题时，**核心策略是：绝不能从零开始解释或发起新查询，必须直接引用前面演示中已经产生的数据和对象来回答**。这样既让演示连贯自然，又让用户直观感受到概念的落地，而非停留在抽象描述。

### 2.1 "什么是对象？什么是视图？"

**复用策略**（前提：已完成结构化本体演示 — 产品对象、订单对象、产品订单视图已创建）：

- **不操作**：不要从头解释概念，不要发起新的创建操作。
- **直接引用**：指着前面创建的 `product` 对象说"这就是对象——相当于数据库里的一张表，定义了数据结构和存储方式"；指着 `product_order_view` 视图说"这就是视图——它关联了产品对象和订单对象，定义了跨表的查询逻辑"。
- **用已有数据对比**：产品对象中存了"数据工厂平台"的字段信息；产品订单视图中，一次查询就能看到"数据工厂平台"的产品信息 + 对应的订单汇总——拆开看是两个独立对象，合起来看是视图。
- **一句话总结**：对象存数据，视图查数据——对象是"仓库"，视图是"窗户"。

### 2.2 "查询快在哪里？有什么特别之处？"

**复用策略**（前提：已完成产品订单视图创建并执行过查询）：

- **不操作**：不要发起新的性能测试查询。
- **直接引用**：回顾刚才演示的产品订单视图查询——一次调用，秒级返回各产品的订单汇总。
- **对比说明**：如果不用视图，传统做法是——先查出所有产品编码，再对每个产品编码去订单表查订单，最后手动汇总；这中间有多少次网络往返？视图把"多次查询"变成了"一次查询"。
- **进一步说明**：用户能看到的是"快"，看不到的是背面的 DSL 规则引擎——简单查询直接命中规则路径，跳过了大模型推理的耗时环节。
- **一句话总结**：本体视图预设了关联逻辑 + DSL 引擎绕过推理耗时 = 又快又准。

### 2.3 "你用了本体吗？本体解决了什么问题？"

**复用策略**（前提：已完成结构化本体和非结构化本体的创建）：

- **不操作**：不要讲解本体理论。
- **直接展示**：列出前面演示中已创建的所有本体对象——`product`（产品）、`order`（订单）、`product_order_view`（产品订单视图）、`visit_record`（拜访记录）。这就是本体，已经在用。
- **逐一解释本体解决了什么**（每个点关联已创建的具体对象）：
  - **统一数据接口**：无论是查客户（来自 CRM 数据库），还是查拜访记录（来自知识库文档），入口都是同一个查询工具——本体屏蔽了底层数据源差异。
  - **跨表关联简化**：产品订单视图一次查询跨了产品表和订单表——本体预设了关联关系，用户不需要知道 JOIN 怎么写。
  - **权限隔离**：每个本体对象可以独立设置访问权限——产品对象只对产品团队开放，订单对象只对销售团队开放。虽然权限插件还在建设中，但本体的权限模型已经预留。
- **一句话总结**：本体就是你对数据世界的"管理面板"——统一入口、预设关联、权限可控。

### 2.4 "结构化数据和非结构化数据怎么融合？"

**复用策略**（前提：已完成客户查询和拜访记录创建）：

- **不操作**：不要发起新的融合查询或打开多个窗口。
- **直接引用**：指着前面创建的结构化客户数据和非结构化拜访记录。
- **解释融合机制**：
  - 客户表（结构化）中每条客户记录有"客户编码"字段。
  - 拜访记录（非结构化）通过"客户名称"字段与客户建立关联。
  - 本体语义层将"客户编码"与"客户名称"做了映射，所以即使字段名不同，系统也知道它们指向同一个业务实体。
  - 当用户查询"广州国投中债"时，系统同时拉取该客户的结构化字段和关联的拜访记录文档摘要。
- **一句话总结**：结构化给数据"骨架"，非结构化给数据"血肉"，本体语义层做"拼接"——同一个实体的不同形态数据被打通。

### 2.5 "多跳数据查询怎么实现的？"

**复用策略**（前提：已完成数据操作演示 — 客户录入和商机任务创建）：

- **不操作**：不要发起新的多跳查询。
- **直接引用**：用前面数据操作演示中实际产生的数据链——那条客户 → 商机 → 任务的关系链。
- **逐跳展示**：
  - 第 1 跳：客户"广州国投中债"（已录入）。
  - 第 2 跳：该客户关联的商机（已从周报中抽取）。
  - 第 3 跳：该商机对应的待办任务（已创建）。
- **解释路径**：客户编码 → 通过商机表的外键关联找到商机 → 通过任务表的关联字段找到任务。本体视图预先定义了这条关联路径，所以查询时系统一走到底，用户只需问"这个客户有哪些商机和任务？"。
- **扩展说明**：实际业务中多跳可以更长——客户 → 商机 → 任务 → 销售 → 组织，任意跳数，本体视图预定义即可。
- **一句话总结**：多跳查询就是把"A 关联 B，B 关联 C"的路径提前定义在视图中，查询时一次走完。

### 2.6 "数据安全怎么保证的？"

**复用策略**（前提：已完成数据操作演示中的确认环节）：

- **不操作**：不要重新演示确认流程或展示安全配置界面。
- **直接引用**：回顾客户录入环节中的确认步骤——用户看到录入预览后，需要点击确认，数据才真正写入。
- **分层说明**：
  - **操作确认（已落地）**：任何增、删、改操作，执行前必须弹出确认表单，由人工审核。查询类操作（只读）自动执行，无需确认。"查询自动，操作确认"——边界清晰。
  - **权限校验（建设中）**：权限插件在确认之前增加一层校验——用户只能查看和操作自己权限范围内的数据。例如销售只能看自己名下的客户，不能越权访问其他销售的客户数据。
  - **审计日志**：所有数据操作均有日志记录，可追溯谁在什么时间做了什么操作。
- **一句话总结**："操作前一定确认"是第一道防线，"权限隔离"是第二道防线，"日志审计"是最后的安全网。

## 三、快速演示清单（10 分钟版）

适用于时间有限的场景，聚焦核心亮点，精简次要环节。

| 时间 | 阶段 | 演示内容 | 核心目标 |
|------|------|---------|---------|
| 0-2 min | 数据查询 | 查 2 条客户数据，展示名称、编码、行业、省份 | 让用户第一时间感受"自然语言→数据"的魔力 |
| 2-4 min | 歧义处理 | 查询含"商机贡献度"的商机信息，展示追问澄清 | 展示系统不是死板应答，而是智能交互 |
| 4-7 min | 本体创建 | 创建产品对象 + Mock 数据 + 产品订单视图 → 查询视图 | 展示"自己建模"的能力，这是核心差异化 |
| 7-9 min | 数据融合 | 展示结构化客户 + 非结构化拜访记录的联合查询 | 展示融合能力，收尾高光点 |
| 9-10 min | 收尾 | 一句话总结五大产品理念，留联系方式 | 让用户记住核心价值 |

**10 分钟版的取舍原则**：

- **保留**：数据查询（入门体验）、歧义处理（智能感）、本体创建（核心能力）、数据融合（差异化亮点）。
- **跳过**：数据统计（可从查询中一笔带过）、数据操作（流程长）、非结构化本体单独创建（融合查询中覆盖）。

## 四、详细演示清单（30 分钟版）

适用于正式演示或深度交流场景，完整展示六大能力 + FAQ 应答 + 产品理念讲解。全程遵循"先演示，后解释"的原则——每个能力演示完后再补充说明原理。

| 时间 | 阶段 | 演示内容 | 关键技术点 | 备注 |
|------|------|---------|-----------|------|
| 0-2 min | 开场 | 引导话术，介绍六大能力，询问用户想从哪项开始 | — | 让用户有掌控感 |
| 2-5 min | 数据查询 | 查 2 条客户，展示常用字段；可补充一次行业筛选查询 | 自然语言→本体视图映射→结果返回 | 如果用户有特定查询需求，优先满足 |
| 5-8 min | 数据统计 | TOP 3 客户（按项目数），补充一次省份分布统计 | 聚合语义理解、排序、分组 | 与数据查询形成对比：一个查明细，一个做聚合 |
| 8-12 min | 歧义处理 | 查询含"商机贡献度"的商机信息；可追加演示"预测-签约<20万"的公式过滤 | 非标准字段识别、候选追问、上下文继承 | 重点展示"追问"环节的交互设计 |
| 12-18 min | 数据操作 | 生成周报 → 信息抽取 → 校验纠错 → 客户录入确认 → 商机任务创建 | 非结构化→结构化、数据校验、确认流程 | 这是最长的环节，环环相扣，不要跳步骤 |
| 18-22 min | 结构化本体 | 创建 product/order 对象 → Mock 数据 → 创建 product_order_view → 查询视图 | 对象定义、视图关联、跨表查询 | 演示完立即执行一次视图查询，感受速度 |
| 22-26 min | 非结构化本体 | 创建 visit_record 对象 → Mock 数据 → 展示与客户的结构化融合查询 | 知识库绑定、结构化+非结构化联合 | 与结构化本体打通，展示融合能力 |
| 26-28 min | 产品理念总结 | 对照五个 README 理念，回顾刚才演示中每个理念对应的具体环节 | 理念→落地映射 | 用户问"本体解决了什么"等问题时，直接用演示数据回答 |
| 28-30 min | 自由交流 | 回答用户问题，补充 FAQ 场景 | — | FAQ 问题直接用演示数据回答，不新开查询 |

**30 分钟版的时间分配建议**：

- 数据操作（周报→录入→任务）占用时间最长（约 6 分钟），因为涉及多个子步骤。
- 歧义处理可根据现场反馈适当拉长——这是最具"智能感"的环节。
- 如果用户中途提出 FAQ 类问题（如"对象和视图有什么区别？"），直接在当前环节用已产生的数据回答，不要等到最后的概念解释阶段。
- 最后 2 分钟的产品理念总结很重要——让用户把零散的演示串联成整体认知。
